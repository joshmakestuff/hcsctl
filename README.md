# hcsctl

A CLI over the Windows Host Compute Service, built on [Microsoft/hcsshim](https://github.com/Microsoft/hcsshim).

Scope: every feature in every hcsshim package this tool depends on, as a CLI you can drive from
a shell or an agent. Images, layers, containers (Hyper-V and process isolated), full virtual
machines, the HCN network lifecycle (list, inspect, create, remove) and a guest agent
(`hcsguest`: info, exec, port forward, network config over Hyper-V sockets) work today. The
legacy HNS networking API surface is excluded; HCN supersedes it.

**[Issue #1](https://github.com/joshmakestuff/hcsctl/issues/1)** is the scope index. Outstanding
work and priority live in the individual [issues](https://github.com/joshmakestuff/hcsctl/issues).
The command inventory comes from `hcsctl help`.

Pull an image and run something in an isolated container:

```
hcsctl image pull   --ref mcr.microsoft.com/windows/servercore:ltsc2022
hcsctl image import --ref mcr.microsoft.com/windows/servercore:ltsc2022   # elevated
hcsctl container run --ref mcr.microsoft.com/windows/servercore:ltsc2022 \
                     --cmd "cmd /c ver"                                   # elevated
```

Process isolation (argon) is opt-in and elevated at every start, and the image build must fall
inside the host's compatibility window (`hcsctl info` reports both per image):

```
hcsctl container run --ref mcr.microsoft.com/windows/servercore:ltsc2025 \
                     --isolation process --cmd "cmd /c ver"              # elevated
```

Publish a TCP or UDP port when creating an endpoint on an HCN NAT network:

```
hcsctl container create --ref mcr.microsoft.com/windows/servercore:ltsc2022 \
                        --network my-nat --publish 39082:8082/tcp           # elevated
```

Port publishing is set when the endpoint is created; the mapping cannot be changed at runtime.

The command surface is generated by the binary: run `hcsctl help` (or `hcsctl help --json` for
its document form).

`--json` puts exactly one document on stdout, progress on stderr. Exit codes: `0` ok, `1` ran
and failed, `64` bad arguments with nothing attempted. A guest process's own exit code is
reported as `exitCode` in the result document, never as hcsctl's exit code.

## Guest agent

`hcsguest` runs inside a VM as a service and answers `hcsctl guest info|exec|forward` and
`hcsctl vm ip|netconfig` over a Hyper-V socket. The socket needs no NIC, no DHCP lease and no
elevation on the host. Release assets ship `hcsguest-windows-amd64.exe` and
`hcsguest-linux-amd64`; [`install/`](install/README.md) has the in-guest installer scripts. Use
the same release tag for host and guest: they share the wire protocol.

## Elevation and isolation

**`image import` is elevated.** Extraction needs `SeBackupPrivilege` + `SeRestorePrivilege`,
both removed from a UAC-filtered token. `ProcessBaseLayer` additionally needs an enabled
`BUILTIN\Administrators` SID, which no user-rights assignment supplies in a filtered token.
`hcsctl info` reports what your token holds.

`container` builds both Hyper-V-isolated (xenon) and process-isolated (argon) containers;
hyperv is the default. A xenon lets the guest be an older Windows build than the host. An argon
stacks the layers on the host and, on every start, needs an enabled `BUILTIN\Administrators`
SID plus an image build inside the host's process-isolation compatibility window — `hcsctl info`
reports both per image. See
[#8](https://github.com/joshmakestuff/hcsctl/issues/8).

## Build

```
go build -o hcsctl.exe .
```

Windows only. Requires Go 1.26+ (the floor is `go.mod`'s directive; CI builds from it).
