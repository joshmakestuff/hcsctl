# hcsctl

A CLI over the Windows Host Compute Service, built on [Microsoft/hcsshim](https://github.com/Microsoft/hcsshim).

The goal is to surface every feature in every hcsshim package this tool depends on, as a CLI you
can drive from a shell or an agent. Images, layers, containers (Hyper-V and process isolated), full virtual
machines and the HCN network lifecycle (list, inspect, create, remove) work today; the rest is

ordered, not dropped. The one exclusion is the legacy HNS networking API surface, which HCN
supersedes. AspireHcs already drives hcsctl, but neither repo's current needs determine this
scope or excuse leaving part of the dependency surface unowned.

**[Issue #1](https://github.com/joshmakestuff/hcsctl/issues/1)** is the scope anchor and
source-of-truth index. Outstanding work and priority live in the individual
[issues](https://github.com/joshmakestuff/hcsctl/issues); the current command inventory comes from
`hcsctl help`. Measured evidence is in the workspace's `docs/findings.md`, beside this repo.

Pull an image and run something in an isolated container:

```
hcsctl image pull   --ref mcr.microsoft.com/windows/servercore:ltsc2022
hcsctl image import --ref mcr.microsoft.com/windows/servercore:ltsc2022   # elevated
hcsctl container run --ref mcr.microsoft.com/windows/servercore:ltsc2022 \
                     --cmd "cmd /c ver"                                   # elevated
```

Process isolation (argon) is opt-in and elevated at every start, and the image build must fall
inside the host's compatibility window (`hcsctl info` reports both per image):

```
hcsctl container run --ref mcr.microsoft.com/windows/servercore:ltsc2025 \
                     --isolation process --cmd "cmd /c ver"              # elevated
```

Publish a TCP or UDP port when creating an endpoint on an HCN NAT network:

```
hcsctl container create --ref mcr.microsoft.com/windows/servercore:ltsc2022 \
                        --network my-nat --publish 39082:8082/tcp           # elevated
```

Port publishing is installed when the endpoint is created; runtime mapping mutation is not
currently supported.

The current command surface is generated by the binary: run `hcsctl help` (or
`hcsctl help --json` for its document form). Keeping a second command inventory here caused it
to drift from the executable contract.

`--json` puts exactly one document on stdout, progress on stderr. Exit codes: `0` ok, `1` ran
and failed, `64` bad arguments with nothing attempted. A guest process's own exit code is
reported as `exitCode` in the result document, never as hcsctl's exit code — those two things
mean different things and conflating them makes `--json` unusable.

## Elevation and isolation

**`image import` is elevated, permanently.** Extraction needs `SeBackupPrivilege` +
`SeRestorePrivilege`, both UAC filtering triggers. `ProcessBaseLayer` additionally needs an
enabled `BUILTIN\Administrators` SID — a group check no user-rights assignment satisfies in a
filtered token. `hcsctl info` reports what your token actually holds.

`container` builds both Hyper-V-isolated (xenon) and process-isolated (argon) containers;
hyperv is the default. A xenon lets the guest be an older Windows build than the host. An argon
stacks the layers on the host and, on every start, needs an enabled `BUILTIN\Administrators`
SID plus an image build inside the host's process-isolation compatibility window — `hcsctl info`
reports both per image. See
[#8](https://github.com/joshmakestuff/hcsctl/issues/8) and the workspace's `docs/decisions.md`.

## Build

```
go build -o hcsctl.exe .
```

Windows only. Requires Go 1.26+ (the floor is `go.mod`'s directive; CI builds from it).
